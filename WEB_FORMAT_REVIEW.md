# Website format review — 1 October 2026

Status: discussion before conversion. Reviewed AGENTS.md, web_format.md, HANDOFF.md, linked layout/answer/animation specifications and current build dependencies. No website transition has begun. Recommendations below are proposals, not accepted decisions. The reference T-Level site has not yet been cloned or audited; that is the next research step after this discussion, before selecting an implementation approach.

## Main decisions

1. **Website deliverables versus the existing publishing contract.** AGENTS requires topic and combined PowerPoints and separate HTML answers; web_format.md lines 7–9 moves slides into website sections. Does the website replace ongoing PowerPoint generation, or must both remain maintained? Recommendation: preserve current files as the migration reference, then make the website the maintained product; agree separately whether printable/exportable resources are needed. Keep mathematical, teaching and content-preservation rules; rewrite format-specific requirements after agreement.

2. **Slide preservation versus adaptive practice.** AGENTS specifies three simultaneous Start/Build/Confidence columns, two scaffolded slides, nine error examples and four independent slides of at least 18 questions each. web_format.md lines 38 and 64 describes up to three pages per Practice set, normally ten adaptive questions per page. These can coexist as different views, but not as one unchanged page model. Recommendation: retain every accepted question and stable reference in banks; distinguish the full topic learning sequence from a short Practice set. Decide whether a teacher projection view retains the three-column layouts and arrows. Keep four-question assessments and nine-example error banks as explicit exceptions to the normal ten-question session; do not silently pad or discard content.

3. **Promotion confirmation is incomplete.** Lines 51–55 combine a rolling ten-answer window with the remainder of a ten-question page. Promotion after question 6 would require four successes; after question 9 only one; after question 10 none. Does any wrong answer immediately revert, and does confirmation continue onto the next page? Recommendation: use a fixed, agreed number of questions at the proposed higher level, carrying the trial across pages. This changes the literal remainder-of-page rule, so needs a decision. Also define the highest-level behaviour and prohibit repeated promotions during an unresolved trial.

4. **Success-rate calculation and eligibility.** The weights are internally consistent: oldest to newest `[1,1,1,1,1,2,2,3,3,3]`, total 18; strictly above 75% means at least 14/18. The stated five/six consecutive-correct examples assume every other answer in the window is wrong. Specify what happens before ten eligible answers, whether old attempts resume when returning to a level, and whether assessment, scaffolded, hinted, retried or revealed answers qualify. Recommendation: a weighted recent-success label, count first submitted independent attempts, keep other practice records separately, and require ten eligible attempts before the first automatic promotion. Invalid input should not count as an attempt.

5. **Progress belongs to a topic or a topic plus page type?** Lines 51–56 describe topic-level success and challenge; line 65 allows different levels per topic/type while initially copying the previous page's level. Recommendation: keep separate state per subject/topic/question-page-type, with history per challenge level. Existing saved state should win; inherit the preceding page's level only for a previously untried type. Mixed-priority pages need an explicit rule: attribute each answer to its actual topic, and decide how the mixed page's overall difficulty is chosen.

6. **Reversion, display and reassessment.** Line 55 freezes the displayed lower-level percentage for the rest of a session but also calls for normal score updates during the next five-question reassessment. Define whether higher-level failures affect lower-level history, whether the lockout starts immediately or on the next matching page, and whether refresh/navigation resumes it. Recommendation: keep levels' histories separate, display the actual rate with a clear trial/reassessment status, persist the five-question lockout, and prevent navigation from bypassing it. If a frozen figure is wanted, label it as the previous-level result rather than a live percentage.

7. **Manual difficulty changes.** Does “after 2” easier questions mean consecutive questions, the same lower level, within one session, or cumulative? Can Confidence drop straight to Start? Does manual advancement bypass or trigger provisional confirmation, and does “below 50% after 10” use the weighted score? Recommendation: two consecutive submitted questions at the same lower level change the recommendation to that level; evaluate manual upward choices after ten eligible attempts at the chosen level. Decide whether this is a recommendation-only path or shares automatic reversion. Define how a change interacts with a pending trial/reassessment.

8. **Practice codes versus adaptive delivery.** A code now identifies up to three collections by type/level, but adaptation changes levels during a page. Decide whether the code promises identical questions, a reproducible initial selection, or only the same practice configuration. Nine characters alone does not define an encoding or compatibility policy. Recommendation: subject selection plus the code identifies the configuration and starting level; adaptations are personalised. Preserve permanent question IDs independently of codes. Decide whether codes must work without a separately selected subject, whether old T-Level codes remain compatible, and what bank changes do to existing codes. Verify the reference implementation before designing the scheme.

9. **Auto-marking and answers/hints.** A final-answer text field cannot verify the written method or the first wrong step in an error example. Define accepted equivalent fractions/decimals, mixed numbers, negative signs, units/currency, labelled paired quantities, ratio order, remainder formats and rounding. Decide what error-spotting requires: corrected answer, identified step, explanation, or a combination. Recommendation: structured answer rules per question; mark final-answer correctness separately from method completion. The sketch check is a reminder only. Keep complete worked solutions available, with hints/reveals disabled during initial assessment to preserve AGENTS' no-hints requirement; decide when feedback is revealed and how it affects progress.

## Further boundaries to settle

10. **Release scope.** The feature list mentions puzzles, themes, issue reports, timers, priorities and gamification without specifying their initial behaviour. “This could potentially be a v2 feature” at line 58 could mean all animation or just user-entered demo values. Recommendation: agree a first-release checklist; static worked examples and student practice/progress first, with animation and custom-value demos explicitly assigned a release. The old animation plan targets native PowerPoint timing; retain its teaching sequences, but replace its technical plan for the website. Define priority ranking and rewards rather than inferring them from the T-Level site.

11. **Drawing persistence and accessibility.** “Clear” on the next question could mean delete the previous sketch or show an empty canvas for the next question while retaining the previous one. Recommendation: keep sketches during the active session and restore on back-navigation; decide separately whether to persist across visits. Provide a typed-working option and an explicit paper-working route, so a blank canvas does not repeatedly prompt students using those routes. Set a meaningful keyboard, screen-reader, contrast and reduced-motion baseline. At 768px, three panels may make working diagrams unreadable: use available space and minimum usable widths, not only the breakpoint, to decide whether the technique reference is a sidebar or overlay.

12. **Local profiles.** The username/local-storage direction is clear: these are device/browser-local profiles, not accounts or cross-device synchronisation. Define case/space normalisation, rename/delete/reset, and optional export/import. Suggest near matches but never automatically merge profiles. The subject selector should be remembered per profile. Decide whether sketches, unfinished sessions and timers are also restored on switching profiles.

13. **Assessment placement and learning sequence.** Does a fresh profile always start at Start, or can the four-question initial assessment set its initial recommendation? Can returning students jump directly into independent practice? Recommendation: separate placement from the ten-question independent-practice promotion system; agree placement criteria and whether prerequisites are recommended or enforced.

14. **Site boundary and reuse.** Is this an independent Maths deployment built for future subjects, or a modification of the existing multi-subject T-Level deployment? This affects code compatibility, storage keys and migration. Recommendation: review a separate clone first; do not change the live T-Level site. Confirm hosting, offline expectations and issue-report destination after inspecting the code. School configuration can be declarative data, but “JSON in a JS file” should be resolved to one documented format; banner/popup/separate-page modes need dismissal and display-frequency rules.

15. **Authority during migration.** AGENTS says preserve manual slide edits and maintain exact Markdown; the current combined PowerPoint has uncommitted changes. Reconcile combined deck, topic decks and source before extracting website banks. Do not assume the latest source or saved topic decks contain those combined-deck changes. HANDOFF's next task (M06) is superseded for now by this review. Historical content notes and the animation plan still contain obsolete workflow assumptions; update them after format decisions rather than treating every historical instruction as current.
