# Spot-the-error teaching and authoring process

## Purpose and agreed approach

Reinforce understanding of each method, accurate application and accurate checking of working. The student must locate and explain **independent method errors**, then complete the corrected calculation. A wrong answer or later wrong working caused by an earlier mistake is a consequence, not another error to identify. Calculation, sign, transcription and place-value mistakes within a method also count: “method error” does not mean only choosing the wrong operation.

## Student interaction and rationale

Keep the student introduction concise: **“Check the working, find the error(s). Click/tap where you find them and choose the reason.”** Do not repeat the detailed interaction or causal-marking rules above the working; the following rules guide implementation and feedback.

1. Select a meaningful location in the displayed working. Correct and incorrect locations must both be selectable; clickable areas must not reveal where mistakes are. Show a thick chisel-tip marker behind the working and a plain location label: slanted ends with 3px rounded outer corners, a bow of 3% of the stroke length, a slight downward diagonal over cells/totals, and a near-vertical stroke along the right-hand factor. Avoid rectangular selection borders that resemble extra lattice cells. The marker uses the error-canvas marker token: equal parts #e0c113 yellow and theme surface, with sufficient contrast against its paper. Include empty positions where something may have been omitted.
2. Choose a short explanation/repair from a dropdown. Choosing it records the entry automatically, with a numbered diagram marker and matching visible list entry. Keep options plausible and specific, without revealing which location is actually wrong. Avoid an extra Add button.
3. Select more locations as needed. The visible list remains available; use its Edit action or the location dropdown to revise an explanation. Tapping/clicking an already highlighted diagram location deselects it and removes any recorded explanation there; the same toggle applies to keyboard activation. The explicit Remove action also clears its marker. Use one entry per location; do not silently overwrite an entry at another location or create duplicates. Sort recorded locations in method-reading order, while accepting any discovery order.
4. The student decides when all errors have been found, enters a **Corrected answer**, and selects **Check answer**. Do not preallocate boxes, announce an expected error count or show correctness before checking. A numbered marker is a selection number, not evidence of correctness.
5. Use the existing correct/incorrect colour tokens after checking for recorded explanations, the current repair choice, corrected answer and overall feedback. Include text feedback so colour is not the only cue. Before checking, markers indicate selection only; editing/removing an answer clears stale marking.
6. Keep the original incorrect working unchanged while the student investigates. Do not automatically repair it after a selection: that can reveal later answers or obscure consequences. On checking, distinguish wrong location, consequential error, wrong explanation, missed independent mistake and incorrect final answer. Allow revision before submission. Live practice retains its existing single scored submission per question; the isolated prototype also permits repeated unscored checks. Correctness requires all independent errors with suitable repairs, no extra incorrect selections, and the correct final answer.

Locating the mistake tests inspection; explaining/repairing it tests method knowledge; deciding when to stop tests thorough checking; the corrected answer tests accurate application. Showing a persistent editable list reduces memory demands. Short repair wording can include the reason (“Carry missed — include it in this diagonal’s total”) without requiring two repetitive dropdowns.

## Method-specific locations

- **Lattice:** the right-hand factor, product cells and diagonal-total/carry regions. Include correct cells, correct totals, consequentially wrong totals and empty carry positions. Select generous areas instead of tiny digits. A diagonal region may group its carry and output digit; the explanation identifies which part is mistaken.
- **Bus stop:** quotient/working positions, remainder transfers and decimal placement. An omitted zero or carry must still have a selectable position.
- **Equations:** working lines and errors within them, not just operation selection. Cover arithmetic/sign errors, coefficient handling, expansion, collection and balance. A line selection plus explanation may identify the particular term/calculation; finer selection is useful only when it improves clarity. Do not treat a valid alternative method as a mistake.
- **Other calculations:** meaningful steps or statements about quantities/units. Choose granularity from realistic student misconceptions, not a universal control template.

The shared UI offers both named keyboard-operable diagram buttons and a location dropdown. The dropdown is hidden by default behind a **Choose by location** link-style button, which toggles its visibility with an accessible expanded state. Hiding it preserves the selected location and diagnoses; Start again and a new question reset it to hidden. The dropdown is a text-based alternative for screen-reader navigation, understanding region names and avoiding precise pointing; it is not a required second selection after tapping. Keep both controls synchronised.

Every pointer target needs a named keyboard-accessible equivalent. Use visible focus, text labels and selection numbers alongside colour. Target sizes must suit phones, and selection lists/options must wrap. Preserve the existing theme tokens and shared control styling.

## Authoring and mathematical review

1. List and agree common mistakes for each topic/method in its spec. Use those mistakes to design varied, level-appropriate erroneous working. Keep the number of independent mistakes separate from the number of wrong displayed values.
2. Store the displayed working and the assessed independent errors explicitly. Propagate the consequences of a mistake through later arithmetic consistently. Do not let a correct-working generator silently repair an intentional fault, and do not introduce accidental extra mistakes.
3. Derive short, distinct explanation/repair options from the agreed misconceptions. Each assessed location must have one correct option. Test each option against both the displayed values and its proposed repair: Keep fine distinctions when the choices remain clear and mutually exclusive; combine them only when they create overlapping or confusing diagnoses. For lattice cells, use “The product is wrong” for both incorrect multiplication and reversed tens/units; keep reversed digits as examples within that family, with specific corrective feedback. Do not offer these as separate competing reasons; never reject a mathematically valid explanation merely because another is more specific. If distinct truthful explanations cannot be avoided, marking must accept them all. Check numerical coincidences too: for example, nearest-integer rounding can accidentally give the correct complete-pack count even though context should determine rounding. Distractors must be wrong for the actual example: a generally faulty approach can accidentally be valid for particular numbers. When a repair could refer to either the original expression or an already altered result, name the intended expression explicitly (for example, the original numerator and denominator). Options at correct locations must remain plausible, so their availability does not disclose the answer.
4. Check the original answer independently, the displayed wrong calculation, every fault's location/type and its downstream consequences. Check that removing the independent faults produces the correct working. Review multi-error cases together: one fault must not mask, cancel or accidentally create another assessed fault.
5. Preserve stable live question IDs, source provenance and submitted history when subsequently migrating content. A prototype is not approval to replace all current banks.

## Lattice prototype boundary

Use the existing generated inline-SVG arithmetic renderer, supplied with explicit setup/cell/carry faults and consistently recomputed consequences. SVG remains suitable for scalable, CSS-styled interactive diagrams; separate image files are the limitation here, not the format itself. Share geometry with the correct demo instead of placing hand-measured hotspots over historical images.

Prototype five examples: one wrong cell product; one omitted carry; two independent mistakes; right-hand digits written bottom-up; and an oversized carry read as an extra answer digit. The last two were explicitly requested after initial review. Reversed setup must drive all cell products and subsequent totals consistently. Oversized-carry working must visibly show a full-size carry and its inclusion as an extra digit in the stated answer; distinguish this from adding a carry twice. Only the original setup/carry mistake is assessed, not its resulting wrong cells or answer. Include selectable correct and consequentially wrong regions in every case. Show a static wrong diagram, editable selection list, explanation/repair dropdown, corrected answer and final check. Keep this on a separate review route with no learner-progress writes or live-bank replacement. A fresh example/restart clears only prototype state.
