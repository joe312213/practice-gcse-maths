## Scoring research — 12 October 2026 (proposal, not implemented)

The superseded `go-estimate.js` used shortest orthogonal empty paths: claim a point within four steps of a colour if the other colour is at least two steps farther away. Count owned points and living stones, then add komi to White. This original distance heuristic produces the stepped boundaries in the user's screenshot; it does not read connected safety, eyes, invasions or likely continuations. It is not a standard scoring rule. Recommendation: replace it rather than retune its radius. This research led to the user-authorised GNU Go replacement below.

Established approaches and candidates:

- **Finished-game counting:** identify surrounded empty regions after agreed dead-stone removal, then apply the selected rules. Area counts stones plus territory; Japanese-style territory counts territory plus prisoners and treats seki differently. [British Go Association comparison](https://www.britgo.org/rules/compare.html). The current app uses area counting; 6.5 komi alone does not make it Japanese rules.
- **Goscorer (pure JavaScript, MIT):** focused area/territory scoring, seki and false-eye handling for end positions; requires correct dead marking and sufficiently resolved protective moves. Recommended final-scoring candidate, not an opening/mid-game predictor. [Maintainer documentation](https://github.com/lightvector/goscorer); [OGS ScoreEstimator imports it](https://github.com/online-go/goban/blob/main/src/engine/ScoreEstimator.ts).
- **Monte Carlo estimation / OGS score-estimator (C++ compiled to JS/WASM, MIT core):** play many continuations, accumulate point ownership, with additional life/seki heuristics. Suitable candidate to evaluate for offline estimates. [Core implementation](https://github.com/online-go/score-estimator/blob/master/Goban.cc). OGS's current wrapper calls its local estimator somewhat deprecated and supports remote scoring; do not present this as its best current analysis. [Current wrapper](https://github.com/online-go/goban/blob/main/src/engine/ScoreEstimator.ts). The wrapper is Apache-2.0, distinct from the MIT core. Integration would need an isolated adapter and browser worker, pinned source/build provenance and measured payload/mobile latency; none is benchmarked here.
- **Influence heuristics / GNU Go:** decaying influence with connection barriers, tactical/life status and invasion patterns. This is substantially richer than nearest-stone distance and distinguishes influence from likely territory. [Official influence documentation](https://www.gnu.org/s/gnugo/gnugo_13.html). Not a small drop-in JavaScript scoring library.
- **Neural ownership / KataGo:** predicts expected score and point ownership with neural evaluation/search. Appropriate future stronger analysis, potentially shared with a computer opponent; requires engine/model deployment rather than a simple counting helper. [Official analysis API](https://github.com/lightvector/KataGo/blob/master/docs/Analysis_Engine.md).
- **Tenuki (pure JavaScript, MIT):** separable game engine supporting area, territory and equivalence scoring, dead marking and simple seki detection. Its README labels the API beta and recommends filling neutral points for reliable seki handling. An alternative end-game library, not a mid-game estimator; adopting another full game model is less focused than Goscorer here. [Maintainer documentation](https://github.com/aprescott/tenuki).

Proposed next slice, subject to agreeing approach: distinguish provisional Estimate from final Score; choose/label area versus Japanese-style territory rules explicitly; evaluate OGS against the user's open positions, capture/life-and-death, seki and neutral-region cases before committing to it. Retain player corrections and original board/history. If adopted, reusable rules/adapter stay in the puzzle module, browser worker lifecycle and app controls outside as appropriate. Credit vendored sources and full licences through THIRD_PARTY_NOTICES.md plus original licence files. No hosted service, dependency or new ruleset has been adopted by this research.

## GNU Go on-demand estimator

Supersedes the original distance heuristic above; `rules/go-estimate.js` has been removed. Keep portable engine access in `ui/gnugo-client.js` (exported as `./gnugo-client`); the host supplies its worker URL. `HumanGo` owns loading/error/retry presentation, cancellation on changed position or leaving Count, and the manual agreed-dead area-count alternative. Never apply a stale response to a changed board. A failed engine does not prevent manual counting.

The host distributes GNU Go 3.8 under `static/engines/gnugo/`. Fetch `worker.js`, `gnugo.js` and WASM only when counting with Estimate open territory enabled; no main-thread engine work or remote analysis. The bridge analyses the complete position at reading depth level 5, uses GNU Go's initial influence for the player to move, `whose_territory` ownership classification and `influence_score(..., 1)` for area-score prediction with komi. User-marked dead groups are removed from the input. Predictions may evaluate group life internally but never alter the agreed-dead selections. Label predictions GNU Go estimate; do not present them as official final scores.

Build patches: give `meaningless_*_moves` single definitions for modern C compilers; make native pattern generator and WASM hash words explicitly 32-bit; run native generators, compile their outputs for WASM; use `emar`/`emranlib` explicitly because the old Makefiles otherwise select the host archiver. Emscripten 4.0.22 is pinned. [Third-party notices](../THIRD_PARTY_NOTICES.md) owns complete source/licence/build links. Preserve these assets and notices when replacing the external puzzle repo, or supply an equivalent host engine URL to the portable adapter.

Verification: actual compiled engine on all supported sizes, komi and colour symmetry and open-corner ownership; worker lazy creation, reuse, cancellation and load failure; browser request checks ensuring no engine fetch before Count, ownership rendering and manual-count switching. Browser checks do not establish physical-device performance or rank strength. No computer opponent is implemented.

## Host state and active controls (15 October 2026 audit)

The reported detached-snapshot drag/focus bug from another app does not appear in this host. Non-Go `PuzzlePlayer` mounts the portable controller once: `player.js` gives `bindChallenges` a live `getAnswer: (_, id) => state[id]`, and surviving cover-path gestures re-read that value on every extension/undo. Text/radio edits update controller state and remove stale feedback without calling `draw`, so the active input/caret survives each character. Svelte receives status callbacks, not a per-character `setState` echo. GoPuzzle/HumanGo also supply live getters of their current answers/game.

`$state.snapshot` belongs at the explicit serialisation/history/initialisation boundary, where cloning is intended. Never capture a detached answer object in long-lived gesture callbacks, and never render/replace an input on each edit. The route's keyed remount follows puzzle/variation/history restoration, not the answer. The existing touch-path test now checks extension, backtracking and re-extension across redraws; sequence-input coverage checks multi-character entry, retained DOM/focus/caret, editing after feedback, and answer retention after an intentional hint redraw. No puzzle production patch was required by this audit.
